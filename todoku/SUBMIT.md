## ② 提出作品の概要

### 着目した課題・背景（300字）

東京都には児童手当、ひとり親医療費、居宅介護など、手取りを増やす制度がすでに多い。しかし制度は局・区市町村・施設に分散し、「自分は対象か」を確かめるだけで何時間も消える。申請しない理由は怠慢ではなく、探索コストである。審査基準のソーシャルインパクトが例示する「手取り時間の増加」は、時給換算の残業削減だけでなく、取りこぼした手当そのものでも起きる。ひとり親、乳児の共働き、介護世帯では、届くべき制度の集合がまったく違う。一覧サイトを増やすのではなく、世帯に合わせて制度の側から届ける必要がある。

### サービスの詳細（300字）

とどくは、世帯状況を3問（家族・世帯の形・家計）またはペルソナ1クリックで受け取り、東京都オープンデータに寄せた制度マスタと突合する。出力は適合度％、マッチした理由、対象外のギャップ、手続の次の一歩、探す時間の削減目安、年間の手取り目安である。コア判定は生成AIに任せない。条件はルール化し、理由を機械的に言語化する。デモではひとり親・共働き幼児・介護世帯でランキングが入れ替わることを示す。個人情報はサーバーに送らない。判定は参考情報であり、申請可否は各窓口の正式判定に従う。

### 課題・背景の解決方法（300字）

最適マッチの発想を人ではなく制度に向ける。必須条件が外れた制度は「届く」から外し、近いものだけ参考表示する。これによりチャットで全件を聞く実装より、2分のプレゼンで差分が目に見える。データはカタログ掲載の子育て支援制度レジストリ、医療費公費負担事業等一覧、居宅・介護予防サービス事業所一覧の項目をデモ用JSONに再構成した。許諾待ちの公表ページは使わない。年度末までの社会実装では、レジストリの正式フィールドを取り込み、区市町村の所得制限を段階的に足す。探すUIではなく、届くUIにする。

## ③ 技術詳細

### 技術選定の理由（300字）

短期間で動くデモと、提供されるCloudflare上での公開を優先した。Next.js 16と静的エクスポートにより、APIもデータベースも持たない。制度とペルソナはJSON、判定はTypeScriptの純関数である。審査の技術力は難解な基盤ではなく、適格判定に合理性があることだと読んだ。地図やリアルタイム災害はデータは豊富でも、今年は類似作が集中しやすい。こちらはマッチングと説明可能性に張った。静的配信なので個人情報を集めず、First Stageの一般公開でもリスクが小さい。

### 生成AI等の活用方法（300字）

開発にはCursor等の生成AIコーディングを使った。プロダクトの適格判定には生成AIを使っていない。幻覚で「受給できる」と誤案内するリスクを避けるためである。理由文はルールから組み立てる。将来の拡張として、OpenCode（Cloudflare Workers AI）は「なぜあなた向けか」の言い換えと、手続手順の平易化に限定して使う想定だ。判定そのものはレジストリの条件列をソースオブトゥルースにする。生成AIは検索窓ではなく、説明の最後の1文に置く。

### デモURL・アクセス

ローカル: `cd todoku && npm install && npm run dev` → http://localhost:3000
静的出力: `npm run build` の `todoku/out/` を Cloudflare Pages に配置（チーム申請後のPaidプラン）。
